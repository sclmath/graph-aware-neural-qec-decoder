## 1. 原始缺陷

旧实现把**每一个发生合并的边的 `fault_mask` 直接累加**，既没有 peeling，也没有真正的簇生长语义。后果不是「精度略差」而是**协议级错误**：用 `matching_dem` 重建 check matrix 后可定量验证——表面码 d=3 码容量 p=0.01、2000 shots 中，468 个含缺陷的 shot 里 **456 个（97%）** 的 correction 违反 `H·c = s`。

表面码上因此完全失效：d=3 码容量 p=0.01 为 0.06311（MWPM 0.00214，29×），d=5 为 0.22607-0.47565（MWPM 0.001-0.04，`results/m4/surface_sweep.json` 的旧 `union_find` 列不可用）。

## 2. 忠实实现

按论文 Algorithm 1/2 的三段结构重写：

### 2.1 Half-edge 生长（`_grow`）

- 每个缺陷是一个 parity 为 1 的簇；边界节点是 ground。
- 簇的**波前**按权重升序逐半条边推进：一条边的两个「半条边」都被走过，这条边才成为 **Grown** 并进入 ε'；两个簇的前沿在同一条边上相遇即**融合**（关键：簇会在边中途相遇，而不是等某一方先撞到边界后被冻结）。
- 簇的缺陷数为偶或触到 boundary 即**冻结**（停止生长）；融合使簇重新变奇时**解冻**，并把此前因冻结而推迟的前沿事件重新入队。
- 终止条件：所有簇都冻结。

### 2.2 Erasure peeling（`_peel`）

在 ε' 上剥离：度为 1 且不在综合征中的顶点，其唯一一条边不在 correction 中，直接删去；度为 1 的缺陷顶点则强制取其边，并把综合征在另一端翻转。boundary 顶点永不剥离。

### 2.3 2-core T-join 收尾（`_resolve_core`）

ε' 含环时 peeling 会停在 2-core 上。此时对 core 的最小生成森林做一次 T-join（终端 = 残余缺陷 ＋ 必要时 boundary），保证 correction 仍满足 `H·c = s`。

## 3. 定位到的三个实现缺陷

忠实版本不是一次写对的；下面三个缺陷各自都会让结果明显变差，全部写进代码注释与单测：

| # | 缺陷 | 症状 |
|---|---|---|
| ① | 簇覆盖 boundary 节点时从未置 boundary 标志 | 簇永不因触界而冻结，生长失控 |
| ② | 冻结的簇在融合后重新变奇时**从未解冻** | 大量 shot 以「未匹配的奇簇」结束 |
| ③ | 前沿抵达**已被覆盖**的顶点时，漏把穿越的这条边加入 ε' | ε' 不完整，peeling 停在 2-core，correction 逻辑类判错 |

其中 ③ 最隐蔽：它在 repetition d=5 码容量上造成 104 vs 6 个逻辑错误（17×），单看代码完全正常。

## 5. 成本

Half-edge 生长是每 shot 一次 Dijkstra 式的事件队列（O(m log m)），加上 peeling 与偶发的 2-core T-join。实测 `union_find` 单 shot 延迟：repetition d=3 电路级 10.7 µs（旧实现 33.4 µs，与 BP 打平），表面码 d=3 线路级 304 µs，d=5 线路级 3441 µs。全部低于同配置的 BP。

## 7. 经验与后续

- **「缺少 peeling」只是表象**：真正的失效模式是「簇在边界处过早冻结 + ε' 不完整」这两件事的组合；只补 peeling（T-join 版本）能把 d=5 码容量从 0.219 降到 0.0117，但表面码仍差 9-50×。
- 三个实现缺陷都不是可以用「近似质量」解释的，而是**语义错误**；因此本项的价值主要在正确性，而非精度调优。
- 后续可做：把 half-edge 事件队列批量化以压低 Python 开销；把 `_resolve_core` 的 T-join 换成 core 上的精确最小 T-join（当前用最小生成森林近似）。
